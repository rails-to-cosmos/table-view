#+TITLE: Proposal — Bulk “select all matching” (server pagination v2)
#+OPTIONS: toc:nil num:nil

[[file:../index.org][← Wiki index]] · related: [[file:incremental-render-o1.org][Incremental render → O(1)]]

* Status

*Deferred to v2* — an explicit decision taken during the server-side
pagination design.  The seam it needs, =table-view-page-request=, already
ships.

* Background

In server-paged mode =table-view--rows= holds only the current page, and marks
are cached row snapshots.  Explicit marks and =(bulk . t)= actions already work
across every page visited.  What cannot be expressed by loading is “operate on
*every* row matching the current filter” — the matching set may be 100k rows
that were never fetched.

* Proposal

A *virtual* select-all, resolved by the backend rather than by loading rows.

- A command “mark all matching” that sets a virtual-select-all flag instead of
  marking individual rows.
- Bulk handlers receive a *selection object* rather than a bare row list:
  - =table-view-selection-rows= — the cached, explicitly-marked rows;
  - =table-view-selection-all-p= — whether virtual select-all is active;
  - =table-view-selection-query= — the live sort + filter (from
    =table-view-page-request=), so the consumer issues one backend operation
    (e.g. =DELETE ... WHERE <filter>=) instead of enumerating unloaded rows.
- The indicator shows “all N matching selected”.

* Trade-offs

- The bulk-handler contract grows a selection object.  Keep the common
  explicit-marks path returning a plain row list, so existing =(bulk . t)=
  handlers are unaffected — only virtual select-all needs the query descriptor.
- The backend must be able to act on a filter predicate (true for SQL-ish
  stores; an in-memory =page-fn= can just re-run its own query).
